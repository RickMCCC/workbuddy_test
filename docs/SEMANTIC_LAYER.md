# 语义层设计思考（讨论纪要）

> 本文档记录关于 AI4BI 架构、尤其是**语义层**的讨论与结论。核心结论：**语义层不是"造口径"，而是"整合已有元数据"**。
>
> 状态：讨论中，部分问题待定（见 §6）。

---

## 1. 架构分层的修正

最初把项目分为「text2sql + 可视化配置」两部分，讨论后修正为更准确的两层：

```
┌─ 查询层（把「意图」变成「数据」）──────────────┐
│   意图有两种表达：                             │
│   · 自然语言（text2sql）                      │
│   · 拖拽字段（结构化，无需 NL 理解）            │
│          ↓ 统一产出「结构化查询」               │
│          ↓ 编译 SQL → 数仓 → 数据              │
└──────────────────────────────────────────────┘
                    ↓ 数据
┌─ 可视化层（把「数据」变成「图表/看板」）────────┐
│   图表类型、布局、联动、下钻                     │
└──────────────────────────────────────────────┘
```

**关键结论：**
- 可视化配置本身不产生数据，它**消费**数据；数据来自「查询」。
- 「查询」有两种触发方式：自然语言（text2sql）或拖拽（拖字段本身就是在生成查询，等价于一个 GROUP BY 查询）。
- 所以「可视化配置依赖 text2sql」是不准确的——准确说法是「**可视化配置依赖查询结果**」，而这个查询用嘴说或用手拖都能触发。

## 2. 窄结果 vs 宽探索（核心矛盾）

**矛盾：**
- text2sql 返回的是**针对性结果**（问「UV 和 PV」就给 `UV=1000, PV=5000`，窄、精准、但没法再折腾）。
- 拖拽需要的是**宽数据集**（能自由切换维度、换指标、下钻）。
- 如果每次拖拽都重新查数仓（尤其 Hive 是分钟级），太慢。

**解法：查询层不返回「答案」，返回「分析数据集（cube）」**

用户说「看 A 页面的 UV 和 PV」，不返回两个数字，而是返回一个以合理粒度预聚合的数据集（如"近 30 天 × 渠道 × 设备的 UV/PV"），落本地：

| 动作 | 数据从哪来 | 耗时 |
|---|---|---|
| 回答原问题「UV、PV 多少」 | cube **汇总** | 毫秒 |
| 拖拽「按渠道看」 | cube **本地重新分组** | 毫秒 |
| 拖拽「按设备看」 | cube **本地重新分组** | 毫秒 |
| 拖拽「加转化率」（cube 里没有） | **才触发新查询** | 慢（可接受） |

**核心原则：一次慢查询，换 N 次本地快探索。**

**矛盾为何消失：** text2sql 的「针对性」体现在"选对了指标和维度范围"，而它的「产物」本身是宽的（cube）。查一次，得到"既精准、又够宽"的数据集，答案和探索都从它身上来。

## 3. 数据环境与 cube 来源

用户数据环境：

```
ODS(贴源) → DWD(明细) → DWS(汇总) → ADS(应用/指标)     [Hive/Doris，多层数仓]
                                        │
                                        ▼
                                CK 表（服务层，快查询）
```

每一层都有元数据：字段的**上下游（血缘）**、字段的**口径**、（另有"通道"，含义待确认，见 §6）。

另有独立字典：**字段口径字典**、**看板字典**。

**关键洞察：ADS/CK 服务层本身就是一个"按指标预聚合"的表，就是那个"够宽、够快"的 cube。**
- cube 的粒度不用拍脑袋定，由 ADS/CK 层的表粒度天然决定。
- text2sql 查这个层（宽、快、一次搞定），拖拽在本地继续折腾。
- 「近 N 天走 CK、历史全量走 Hive ADS」的分层路由，正好对应「多层数仓 + CK 服务层」的现状。

## 4. 语义层 = 元数据整合层（核心结论）

**语义层不是从零定义指标，而是整合已有的元数据。** 原料就是：血缘 + 口径字典 + 看板字典。

映射关系：

| 语义层概念 | 从哪里的元数据来 |
|---|---|
| **指标 Metric** | ADS/CK 层的指标字段 + 口径字典里的口径 + 血缘里的上游计算逻辑 |
| **维度 Dimension** | 维度表（DIM）+ 血缘里的关联 |
| **关系 Relation** | 血缘里的「事实表 ↔ 维度表」上下游 |
| **同义词/别名** | 口径字典 + 看板字典里对同一指标的不同叫法 |
| **主题域** | 数仓的分层/主题划分 |

**血缘是最值钱的部分**：它自动回答「指标怎么算的」（口径）、「能跟哪些维度关联」（关系）——这两件事原本要人肉写、最容易出错、成本最高。

## 5. 语义层到底是什么（大白话）

**语义层 = 把「业务叫法」和「数据字段」之间的对应关系，用几张表明明白白记下来。** 具体就是 4 张表：

用 UV/PV 举例，从"散落三处"到"收拢成表"：

**散落状态：**
- 血缘：`dws_uv_pv_di.uv = count(distinct dwd_page_view_di.user_id)`
- 口径字典：「UV = 独立访客数」「PV = 页面浏览量」
- 看板字典：「运营日报」用了 UV/PV，按「日期+渠道」看

**整合后（4 张表）：**

`metrics`（指标表）：
```
code | name | definition(口径) | formula                | table_name    | field_name
uv   | UV   | 独立访客数        | count(distinct user_id) | dws_uv_pv_di | uv
pv   | PV   | 页面浏览量        | count(event_id)         | dws_uv_pv_di | pv
```

`dimensions`（维度表）：
```
code    | name | table_name   | field_name  | type
date    | 日期 | dim_date     | date        | time
channel | 渠道 | dim_channel  | channel_name| category
```

`relations`（关系表）：
```
name       | fact_table    | dimension_table | join_keys
UVPV-日期  | dws_uv_pv_di | dim_date        | dws_uv_pv_di.dt = dim_date.date
UVPV-渠道  | dws_uv_pv_di | dim_channel     | dws_uv_pv_di.channel_id = dim_channel.id
```

`terms`（同义词表）：
```
kind   | term     | metric_id
metric | 独立访客  | (uv)
metric | 访客数    | (uv)
```

**「映射/导入」= 一段导入程序**，自动把三样原料填进这 4 张表：
1. 读血缘 → 填 `metrics` 的 formula/field_name，并把关联填进 `relations`。
2. 读口径字典 → 填 `metrics.definition`。
3. 读看板字典 → 补别名（`terms`），甚至直接导入成种子看板。

导入产物全是**草稿**，经确认后成为"官方指标"（口径统一机制）。

**为什么是地基：**

| 能力 | 语义层起的作用 |
|---|---|
| text2sql | 说「看 UV/PV」，系统只查 `metrics` 表就找到 code/口径/表字段，直接生成查询，准确率暴增 |
| 拖拽 | 左侧字段面板 = `metrics` + `dimensions` 的列表 |
| 口径统一 | 「UV 啥意思」→ 查 `metrics.definition`，一个地方一个答案 |
| 关系 | 「UV 能按渠道看吗」→ 查 `relations` 知道怎么 join |

## 6. 待定问题（需继续讨论）

1. **血缘 / 口径字典 / 看板字典的形态**：是数仓里的元数据表？元数据平台（Atlas/DataHub/自研）的 API？还是 Excel/文档？—— 决定导入方式（SQL 读 / 调 API / 文档解析）。
2. **指标锚定在哪一层**：ADS 层、CK 层，还是「都锚定 + 分层路由」？
3. **「通道」具体指什么**：需用户确认这个词。
4. **text2sql 与拖拽在查询层的关系**：平级入口，还是 text2sql 为主、拖拽兜底（AI-native 路线）？
5. **cube 的粒度上限**：cube 过大（千万级）时，是"截断 + 下钻回查"还是"分层聚合"？
6. **本地数据集缓存生命周期**：换一个问法就失效，还是按"数据集维度"复用？

---

## 7. 与现有实现的关系

- 语义层的 4 张表（`metrics`/`dimensions`/`relations`/`terms`）**已在后端建好**（`apps/server/app/models/semantic.py`）。
- 现有实现是「窄结果」：`/api/query` 问什么就精确返回什么。按本次讨论，**应改为返回「答案 + 够宽的分析数据集（cube）」**，前端缓存后本地探索。
- **导入器**（血缘/字典 → 语义层 4 张表）**尚未实现**，待元数据形态确认后开发。
